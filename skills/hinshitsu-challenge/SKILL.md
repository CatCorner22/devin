# hinshitsu-challenge: 4 lenses and a standing red cell

Part of the hinshitsu contract. `../hinshitsu/GLOSSARY.md` defines every term in capitals. `../hinshitsu/SKILL.md` (the conductor) sets precedence, roles, custody of reports (rules 1.5 to 1.8) and the 12 STAGES. An imperative sentence binds the ORCHESTRATOR; `must` binds the actor named; `may` grants a discretion that nobody else has. Rules are cited by section and number.

This skill holds sections 5 and 6. It serves STAGE S5 (plan-time challenge), each WORK UNIT of S7 (1 LENS memo and any probe), and S9 (pre-delivery attack). Before acting, read sections 0 and 1 of the conductor (`hinshitsu`) and `GLOSSARY.md`; the `STAGE` start entry states the SHA-256 of each (rule 0.7). Without a conductor run this skill produces no verdict: say so to the USER and start the conductor.

Every LENS and every RED CELL is a SUB-AGENT started under rules 1.5 to 1.7: a scope saved under `prompts/` first, a `LAUNCH` entry when the identifier returns, the report saved whole with the runtime's identifier on its first line. The scope is the role text in `templates/roles/` plus file names and the CRITERIA word for word. No LENS and no RED CELL receives the BUILDER's conversation. A `CORE` run skips S5 and S9 and reports every role in this skill UNVERIFIED (rule 0.5).

## 5. Continuous Lens Rotation

1. **The 4 LENSES** and the question each asks:

   | LENS | Question |
   |---|---|
   | Recipient experience | What will each RECIPIENT do with this, step by step, and where does it fail them? |
   | Minimal viable sequence | What is the smallest ordered set of work that meets the CRITERIA, and what is out of order, oversized or not needed? |
   | Structural integrity | Do the parts fit: names, data, contracts, states, and each edge in `CONNECTIONS.md`? |
   | Trust and controls | Who can do what alone, what can be faked or lost, and what stops it? |

2. **At planning.** After the `PROPOSED` `CRITERIA` entry and before the freeze, start 1 SUB-AGENT per LENS, in parallel where the runtime allows. Each receives the `VOC` entry, the `GAP` entry, the `PROPOSED` CRITERIA, the `ASSUMPTION` entries and the plan.
3. **Memo form.** Each LENS writes `memos/lens-<name>.md` with these 5 headings, in this order: `What breaks`, `What to cut`, `What to add`, `The 1 change this lens insists on`, `Checked and found sound`. Every point must cite a file and line or an ID, and every point under `What breaks` must state for whom it breaks and how a third party reproduces it. A memo with no point under `What breaks` is handled as a 0-FINDING report under rule 16.6.
4. **Reconciliation.** Write a `RECONCILIATION` entry: a table with 1 row per memo point and per RED CELL demand, and the columns point (with memo and number), LENS, `ACCEPTED` or `REJECTED`, the CRITERION or decision changed, and the reason. Every point has a row. A `REJECTED` row must state a reason that a third party can test against the brief or the CRITERIA; cost alone is a reason only when the row states the cost. Do not send the S6 card and do not freeze CRITERIA before this entry exists.
5. **During the build.** After the swarm reports on a WORK UNIT, the ORCHESTRATOR must tag each FINDING with the 1 LENS whose question it answers. Then start 1 SUB-AGENT for the LENS whose turn it is (WORK UNIT number modulo 4, in the table's order: 1 recipient experience, 2 minimal viable sequence, 3 structural integrity, 0 trust and controls), and 1 more for any other LENS that received a BLOCKER. Each writes `memos/lens-<name>-<WU>.md` with 3 headings: `Does this WORK UNIT or its FINDINGS change the plan`, `Does it change a CRITERION`, `Does it change a later WORK UNIT`, each answered `yes` or `no` with a citation.
6. **No memo, no completion.** A WORK UNIT with no LENS memo is not complete. Do not start the next WORK UNIT on top of it. A `yes` in a LENS memo becomes a `DECISION` entry, or a DECISION CARD when it changes a CRITERION.
7. **Full synthesis.** Only when the USER asks, or when the RED CELL returns `PLAN KILLED`: start 3 SUB-AGENTS that each write a complete alternative design without seeing the others, then 2 SUB-AGENTS as judges that each score every design against every CRITERION. Save all 5 files under `memos/`, write the chosen design as a `DECISION`, and return to S4.

## 6. Standing Red Cell

1. **Role.** The RED CELL attacks PREMISES for the whole run. It is modeled on the opposing force that Lt. Gen. Paul Van Riper led in Millennium Challenge 2002: it does not accept the planner's framing, and its results stand: the ORCHESTRATOR logs each of its findings as a `FINDING` entry and does not run the role again on the same commit (rule 1.7). A new SUB-AGENT may hold the role at each activation; each one receives the RUN FOLDER and the DELIVERABLE.
2. **Full attack, 2 times.** Run a full premise attack (a) at S5, on the plan, and (b) at S9, on the DELIVERABLE and the record, after the last swarm round. The report, `audits/redcell-plan.md` or `audits/redcell-delivery.md`, must hold: a verdict, exactly 1 of `PLAN SURVIVES`, `PLAN SURVIVES WITH CHANGES`, `PLAN KILLED`, `INSUFFICIENTLY ADVERSARIAL`; each PREMISE attacked; how the DELIVERABLE fails if the PREMISE is false; the EVIDENCE or the named test that settles it; a section `The cheating agent` that states the cheapest way an AGENT could appear to follow the plan without doing the work, and which rule catches it; and the changes demanded.
3. **Probes.** Start 1 RED CELL probe, scoped to the 1 event, on each of these triggers: (a) a request to change a CRITERION; (b) a contradiction found under rule 8.4; (c) a broken edge in `CONNECTIONS.md`; (d) an audit round in which every AUDITOR reports 0 FINDINGS, or in which every FINDING is STYLE. Run at most 1 probe per trigger event. Log each as a `PROBE` entry with the trigger, the `LAUNCH` entry and the result. A probe that returns no FINDING ends there; it does not trigger another probe.
4. **Retroactive attack.** The RED CELL may attack any logged decision, at any time, however old. A decision is never closed to attack. The scope of each full attack must name every `DECISION` entry.
5. **Unflagged premise.** In each full attack the RED CELL must attack at least 1 PREMISE that is absent from every `ASSUMPTION` entry. The attack counts only if it states a concrete failure (who does what, and what goes wrong) and either pastes EVIDENCE or names the test that settles it. The ORCHESTRATOR must not judge whether it counts: the final AUDITOR of rule 17.4, or at S5 any 1 LENS SUB-AGENT given the report and the `ASSUMPTION` entries, records `counts` or `does not count` with the reason. If none counts, the verdict is `INSUFFICIENTLY ADVERSARIAL`: start 1 new RED CELL SUB-AGENT. If that run earns the same verdict, report the red-cell check UNVERIFIED, tell the USER, and do not start a third.
6. **Attack and FINDING.** A RED CELL attack becomes a FINDING only when it states a trigger that a third party can repeat and names the CRITERION or rule that fails. Each such FINDING is a BLOCKER and follows section 14. Log every other attack in an `ASSUMPTION` entry as a new PREMISE with the RED CELL's report cited, and answer it in the `RECONCILIATION` entry.
7. **Premortem.** In the pre-delivery attack the RED CELL must write, under the heading `Premortem`, a story of at least 150 words that begins "Six weeks from now the user reports that this failed." and that names what failed, who met the failure, and which CRITERION, PREMISE or missing check let it through. Each cause the story names is handled under rule 6.6.
8. **Verdict.** The ORCHESTRATOR must not soften, summarize or omit a RED CELL verdict. Quote it, word for word, in the delivery report. On `PLAN KILLED`, stop the build and follow rule 5.7.
